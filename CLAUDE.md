# CLAUDE.md

Context for working on this repo.

## What this is

A Chrome extension that reads a Tango puzzle off the page, solves it in two phases,
overlays the answer on blank cells live, and can replay the derivation as an animation.
`8tango.com` is fully working (read, write, overlay, live animation, autofill, all
verified against real puzzles). `linkedin.com/games/tango` has a verified read path
(cross-checked against a completed puzzle) but an unverified write path, since
LinkedIn only drops one puzzle a day and today's was already solved when the adapter
was written; see "Remaining work."

The math is documented in `README.md` (short version) and `docs/tango_gf2_writeup.md`
(full version). Read the README before changing anything in `src/core/`. Short version:
sun = 0, moon = 1, so a board is a vector in F₂³⁶. Clues, row balance parity, column
balance parity, and givens all become linear equations `Ax = b` over F₂. Gaussian
elimination pins a large fraction of cells for free and detects inconsistency. The two
rules that are not linear (exactly three of each symbol, and no three in a row) survive
elimination and need combinatorial search.

## Layout

```
src/core/          the solver. no DOM access, ever.
  encode.js        board <-> F2 vector, constants, clue normalisation
  trace.js         event schema + recorder
  gf2.js           builds [A|b], Gauss-Jordan to RREF, provenance tracking
  search.js        phase 2 backtracking over the affine remainder
  solve.js         orchestrator
src/adapters/      site-specific board reading/writing, one file per site
  8tango.js        real, verified (read + write)
  8tango-bridge.js MAIN-world helper 8tango.js depends on -- see below
  linkedin.js      real, read verified / write unverified -- see below
src/extension/     the Chrome extension shell (DOM-touching, unlike src/core)
  content.js       entry point: picks an adapter, solves, drives the overlay,
                   publishes state to chrome.storage.local, handles AUTO_SOLVE
  overlay.js       draws solved values over blank cells, non-destructively
  popup.html/js    toolbar popup: status + "Watch the math" + "Auto-solve"
test/
  reference_solver.py   Python implementation, used ONLY as an oracle
  gen_cases.py           emits cases.json from the reference
  crossvalidate.js       compares JS against the reference
tools/
  gen_puzzles.py             picks demo puzzles with verified-unique solutions
  harness-template.html      standalone animation UI, canned puzzles
  build-harness.js           inlines src/core into harness-template.html -> harness.html
  live-harness-template.html same UI, but sourced from a live-solved puzzle
  live-harness.template.js   the UI's JS, kept separate from the HTML (see CSP note below)
  build-live-harness.js      inlines src/core into the above -> dist/live-harness.html + .js
harness.html       generated, do not edit by hand
manifest.json      MV3 manifest: two content_scripts entries, popup, storage permission
docs/              the math writeup
```

`dist/` (content.js, 8tango-bridge.js, live-harness.html, live-harness.js) is a build
output, gitignored, regenerated by `npm run build:extension`. Load the *repo root* as
the unpacked extension in `chrome://extensions`, not `dist/`.

## Commands

```
python3 test/gen_cases.py && node test/crossvalidate.js   # solver cross-validation
node tools/build-harness.js                               # regenerate harness.html
npm run build:extension                                   # regenerate everything in dist/
```

After editing anything under `src/` or `tools/live-harness*`, `npm run build:extension`
and then reload the extension in `chrome://extensions` (see the Chrome gotchas section:
reloading the extension and refreshing the tab are two different, both-required steps).

## Invariants that must not break

1. **`src/core/` never touches the DOM.** The solver emits a flat list of trace events
   and the animator replays them. This is what keeps scraping bugs and math bugs
   distinguishable, and it is what makes the animation scrubbable in both directions.

2. **Cross-validation must stay at 1685/1685.** Any change to the solver gets checked
   against the Python reference before anything else. If the two disagree, the JS is
   wrong until proven otherwise.

3. **Rank 11 on the bare parity subsystem.** Solving an empty board with no clues must
   return rank 11 and free dimension 25. This is a proven property of the problem, not
   an empirical observation, so a change in that number means a bug.

4. **Provenance must stay honest.** Every `cell_pinned` event carries `derivedFrom`, the
   ids of the original equations that combine to force it. XORing those original rows
   together must reproduce exactly `e_cell` with the right RHS. The animation draws this
   as a proof, so it must actually be one.

5. **`harness.html` is generated.** Edit `tools/harness-template.html` and rebuild. Same
   for `dist/live-harness.html`: edit `tools/live-harness-template.html` and
   `tools/live-harness.template.js`, never the generated output.

## Technical gotchas already hit

Solver-level:

- **JavaScript bitwise operators coerce to 32-bit signed integers.** Rows are 37 bits
  (36 coefficients plus the RHS), so packing them into a Number and using `^` silently
  truncates and produces a confidently wrong solver. Rows are `Uint8Array(37)` for this
  reason, and also because each byte maps one-to-one onto a rendered matrix cell.

- **Phase 2 stops unwinding once the solution limit is hit**, so the trace ends with the
  board in its solved state rather than tearing it back down. Do not "fix" this.

Chrome extension-level (all hit and fixed while building the 8tango adapter; expect the
LinkedIn one, or any future one, to hit some of these again):

- **Content scripts run in an isolated JS world.** They share the DOM with the page but
  NOT page-defined JS globals. `window.game` (8tango's entire state) is invisible to an
  isolated-world content script no matter how long you poll for it -- it just silently
  never appears. The fix is `src/adapters/8tango-bridge.js`, declared as a second
  `content_scripts` entry in `manifest.json` with `"world": "MAIN"`, which relays state
  across via a `CustomEvent` (the DOM *is* shared, so events on it cross freely). If a
  future site also keeps state on a JS global instead of the DOM, expect to need the same
  pattern. LinkedIn didn't need this: its board state lives entirely in DOM attributes.

- **A DOM node you append inside a React-managed subtree gets deleted on the next
  render.** The overlay was originally a child of the board element; every single cell
  click wiped the whole overlay, because React reconciles that container's children
  against its own virtual DOM and removes anything it didn't render. Fix: the overlay
  lives under `document.body` with `position: fixed`, entirely outside any framework's
  subtree, and recomputes its own screen position from `getBoundingClientRect()`.

- **A `MutationObserver({childList:true})` does not fire for a plain JS state change**,
  even one that logically "should" cause a mutation soon after. If the framework reuses
  existing DOM nodes and only touches attributes (or doesn't touch the DOM at all until
  its own next tick), waiting for childList mutations can hang forever. Prefer a short
  `setInterval` poll (50ms) for "wait until this condition is true" -- it's not elegant
  but it's the correct tool when what you're waiting for isn't fundamentally a DOM event.

- **Re-solve on puzzle change, not just on cell change.** A content script runs once per
  page load. Starting a new puzzle in-app (8tango's "+" button) doesn't reload the page,
  so without explicit detection the overlay keeps showing the *previous* puzzle's answer
  mapped onto the new puzzle's cells -- wrong values, apparently-broken clues, missing
  marks. Fix: hash the board's givens+clues on every observed mutation and only re-solve
  when that signature actually changes (`content.js`'s `resolveIfChanged`).

- **Extension pages (popup, `dist/live-harness.html`) get MV3's default CSP,
  `script-src 'self'`, which blocks inline `<script>` content entirely.** Content
  scripts aren't subject to this (they're not page-rendered HTML), but any HTML page
  you ship as part of the extension is. `tools/build-harness.js`'s trick of inlining
  everything into one `<script>` tag works for the *standalone* `harness.html` (a plain
  file you open directly, not an extension page) but breaks silently -- as a blocked
  request, not a JS error -- for `dist/live-harness.html`. Fix: keep the JS in its own
  file (`live-harness.template.js` -> `dist/live-harness.js`) and reference it with
  `<script src="live-harness.js"></script>`.

- **`chrome.tabs.query()` results have `tab.url` populated only if the extension has
  host permission for that tab's origin** (via `host_permissions`, or the site's
  presence in a `content_scripts.matches`, or `activeTab`). Without it, `tab.url` is
  `undefined`, which silently breaks any hostname check the popup does on the active
  tab -- it looks exactly like "wrong site," not "missing permission." Every site an
  adapter supports needs to be in `host_permissions`, independently of it already being
  in some `content_scripts.matches` list.

- **Reloading the extension and refreshing the tab are two different steps, both
  required, in a specific order.** Editing files on disk does nothing to a
  already-loaded unpacked extension until you click the reload icon (circular arrow) on
  its card in `chrome://extensions` -- the on/off toggle does not do this. And a page
  that was already open needs an actual refresh after that, since the content script
  that's already injected into it doesn't get hot-swapped. When something "still isn't
  working" after an edit, verify both happened (a build-timestamp marker logged at the
  top of the script is the fastest way to confirm which version is actually running)
  before assuming the code itself is still wrong.

- **A silent, total failure to inject with zero console output and zero
  `chrome://extensions` errors can still just be a bug in a *different* script reading
  the wrong signal**, not a manifest or permissions problem. The LinkedIn popup showed
  "not on 8tango.com" while sitting on the LinkedIn tab; every manifest/permission/CSP
  theory was ruled out one at a time before finding the actual bug: `popup.js`'s own
  hostname allowlist had never been updated when the LinkedIn adapter was added to
  `content.js`. The two files' site lists can drift independently and nothing enforces
  they match.

## Trace event schema

This is the contract between the solver and any consumer (the harness, the live
extension overlay, `dist/live-harness.html`). Adding events is fine; changing existing
shapes is not, without updating every consumer.

```
phase          {phase}                     assemble | eliminate | search
row_added      {block, row, meta, bits, rhs}
pivot_chosen   {row, col}
row_swap       {a, b}
row_xor        {target, source}            target ^= source over F2
cell_pinned    {cell, value, derivedFrom}
rank_update    {rank, freeDim, pinnedCount}
contradiction  {row, derivedFrom}          system asserts 0 = 1
guess          {cell, value}
reject         {cell, value, reason}
backtrack      {cell}
solution       {board}
done           {consistent, rank, freeDim, solutionCount}
```

`block` is one of `row_parity`, `col_parity`, `clue`, `given`.

## Adapter contract

Every site-specific assumption lives behind one interface so that when a site reshuffles
its DOM, exactly one file changes:

```js
// src/adapters/<site>.js
export function matches(hostname) { /* ... */ }
export async function readBoard() {
  return {
    givens: Int8Array(36),      // 0 sun, 1 moon, -1 unknown, row-major (r*6+c)
    clues: [{ a, b, type }],    // flat cell indices, type '=' or 'x'
    boardEl,                    // container to watch for mutations / anchor the overlay
    cellElement(index),         // -> the DOM element for a flat cell index
    isFilled(index),            // -> bool, whether that cell already shows a value
    writeCell(index, value),    // click/set a cell to SUN or MOON
  };
}
```

`content.js` only ever calls this common surface, never anything site-specific, so
adding a third site means writing a new adapter file and adding it to `content.js`'s
`ADAPTERS` list -- and remembering to check `popup.js`'s `isSupportedHost` too (see the
gotcha above; nothing currently keeps these in sync automatically).

### 8tango.com (verified: read + write)

State lives on `window.game`, read through `8tango-bridge.js` (see the isolated-world
gotcha above).

```
window.game.board.spaces[y][x]  0 blank, 1 sun, 2 moon
window.game.prefilled[y][x]     true for the puzzle's original givens
                                 (top-level on game, NOT nested in .board)
window.game.board.modifiers     [{ kind, a:{x,y}, b:{x,y} }]
                                 kind 1 '=' (same), kind 2 'x' (opposite)
window.game.BOARD_SIZE          6 for Free Play; other sizes are Journey-mode
                                 levels the solver doesn't support
```

Cells are `.game-board .cell[data-x][data-y]` divs; class contains `sun`/`moon` for a
filled value. Clue markers (`.modifier.same` / `.modifier.opposite`) are positioned
*absolutely by pixel offset* as siblings of the cells, not nested inside them or tagged
with which two cells they relate -- that's why they weren't highlightable in Inspector.
Recovered the pairing with plain geometry: nearest two cell centers to the marker's own
`getBoundingClientRect()` center. Writes are a real `.click()` on the cell (cycles
blank -> sun -> moon -> blank); the site's handler doesn't check `event.isTrusted`, so a
script-dispatched click works exactly like a real one. The click's *effect* on
`window.game` is synchronous but the resulting DOM re-render lags a tick, so read the
*current* value for computing the click count from the DOM class, not from `window.game`
(which the isolated world can't see anyway).

### linkedin.com/games/tango (verified: read only)

No JS state global was found; everything lives in the DOM, keyed by LinkedIn's own
accessibility markup -- convenient, since it means no bridge script is needed here.

```
[data-cell-idx="N"]             N = row*6+col (row-major). Confirmed via each cell's
                                 aria-describedby target, whose text is literally
                                 "Row R, Column C".
svg[aria-label="Sun"|"Moon"]    child of the cell div; the cell's value. No matching
                                 svg means blank.
aria-disabled="true"            on the cell div: marks an original given.
[data-testid="edge-cross"]      '×' (opposite) clue marker
[data-testid="edge-equal"]      '=' (same) clue marker
```

Clue markers are `<svg>` elements nested *inside* one of the two cells they relate
(`data-testid="edge-cross"`, e.g., sits inside `#tango-cell-19`), not positioned
independently and not carrying the pair explicitly -- same geometry trick as 8tango
(nearest two cell centers to the marker's bounding-rect center) recovers the pairing.

How this was verified without a live/blank puzzle: today's puzzle was already complete
(LinkedIn drops one a day) when this adapter was written. Read all 36 cell values plus
the 6 clue markers, confirmed the completed board satisfies every clue and every
row/column parity constraint (no solver involved yet, just checking the *site's own*
answer is internally consistent by our understanding of the rules). Then took only the
`aria-disabled="true"` cells as givens, fed them plus the clues into `solve()`, and
confirmed the unique solution it found reproduces the actual completed board exactly.
That's strong evidence the read side (cell indexing, given-detection, clue-detection)
is correct.

What's still unverified: `writeCell` (guessed as a `.click()` cycle mirroring 8tango's,
since cells have `role="button"`/`tabindex="-1"` suggesting the same interaction model,
but nothing confirms the cycle order or even that clicking is the right mechanism at
all -- there was no blank cell available to test against). Confirm this against
tomorrow's fresh puzzle before relying on it for autofill on LinkedIn.

## Chrome extension architecture

`manifest.json` has two `content_scripts` entries:

1. `8tango-bridge.js`, `"world": "MAIN"`, `run_at: "document_start"`, matches only
   8tango.com. Exists solely to read `window.game` from inside the page's own JS world
   and relay it to the isolated world over a `CustomEvent`.
2. `content.js`, `run_at: "document_idle"`, matches both 8tango.com and
   `linkedin.com/games/tango*`. The actual extension logic: picks an adapter, solves,
   draws the overlay, publishes to `chrome.storage.local`, listens for `AUTO_SOLVE`.

`host_permissions` lists every site an adapter supports (see the `tab.url` gotcha
above -- this is independent of the `content_scripts.matches` entries).

State handoff to the popup and `dist/live-harness.html` goes through
`chrome.storage.local` under the key `affineTangoPuzzle`
(`{ givens, clues, rank, freeDim, blankCount }`), written by `content.js` every time it
(re-)solves. Nothing polls; the live-harness page also listens for
`chrome.storage.onChanged` so it stays live if you leave it open across puzzles.

Autofill is popup-triggered only (`{type: 'AUTO_SOLVE'}` message to the content script),
never automatic -- CLAUDE.md already flagged that LinkedIn tracks streaks, so silently
changing what a player actually solved themselves would be the wrong default even though
a button push isn't literally a persistent "toggle."

LinkedIn's board ignores untrusted clicks (see the LinkedIn section below), so its adapter
returns `writeCellsTrusted` instead of `writeCell`; `content.js`'s `AUTO_SOLVE` handler
branches on which one the adapter exposes. The trusted path goes through
`chrome.runtime.sendMessage({type: 'DEBUGGER_CLICK_BATCH', points})` to
`src/extension/background.js`, a service worker (added for this reason -- there wasn't
one before) that drives `chrome.debugger`'s `Input.dispatchMouseEvent`. Attaching shows
Chrome's persistent "started debugging this browser" banner on the tab; the background
script attaches right before a fill batch and detaches immediately after rather than
holding it open. This needed the `debugger` permission added to `manifest.json`.
